# Online gift card redemption

Cookie checkout now has an optional gift card flow for carryout, curbside and shipping. The original Square-hosted checkout remains the default and supports its existing coupon and reward redemption controls. The custom gift flow does not implement coupon entry, reward redemption, digital wallets or tipping. Customers see this distinction before choosing. Existing loyalty accounts matching the checkout phone earn points through Square AccumulateLoyaltyPoints after successful payment; no new enrollment happens without consent. Loyalty failures are retried independently of paid orders and payment recovery.

Choose Pay with a Chunki Chip gift card in the fulfillment dialog (or after choosing a shipping rate). Customer contact details are added to the Square fulfillment. Square's gift-card SDK collects/tokenizes the card number; the custom server never receives or stores raw gift card numbers or card details.

The backend uses catalog variation/modifier IDs and Square-calculated totals. Client ad hoc prices are rejected for this flow. Shipping service charges come from the existing signed, address/cart-specific Shippo quote. Orders have actual PICKUP or SHIPMENT fulfillments, and curbside retains its existing arrival check-in. The contact phone number is normalized to US E.164.

A gift card authorizes up to the amount due with autocomplete=false and partial authorization enabled. If it covers the order, PayOrder captures it immediately. Otherwise one additional card authorization covers exactly the remainder; PayOrder captures both. Full order amount/currency/location and payment authorizations are rechecked first. No manual REDEEM activity is posted, avoiding double-debiting the gift card. A changed order total stops the checkout and releases still-approved payments.

Private session credentials are unguessable, stored hashed in the server-only RLS table cookie_checkout_sessions, passed in a header and retained in sessionStorage for refresh/recovery. The initial link uses a URL fragment, then removes it from the address bar. No tokens are accepted as order ownership from a plain order ID. Raw payment nonces are transient only. Payment IDs, idempotency keys, contact details and order references are persisted. A database lease serializes all mutations across instances. Keys are unique per session/attempt and fit Square's limit.

Unknown authorization responses persist an operation key. The customer can release that unconfirmed attempt via CancelPaymentByIdempotencyKey before trying another payment. Already-applied gift reservations remain on the order. A lost PayOrder response is recovered through the persisted paying state, verified payment statuses and the same PayOrder key. Captured payments are never canceled to "recover" a checkout. Unfinished sessions expire after 30 minutes; a 30-second worker releases incomplete authorizations. Outages can delay cleanup until the worker restarts; Square's own authorization expiry still applies. The server must stay running for prompt recovery.

No new environment variables are needed beyond the existing Square application ID/token/location, Supabase URL and server secret key. Schema is recorded in supabase/setup/cookie-checkout.sql; RLS is enabled with no anon/authenticated privileges. Gift card purchase issuance remains a separate flow.

Validation: node --test api/tests/*.test.js and npm run build. Provider interactions are mocked in automated checks. Actual gift redemption, SDK field rendering, split-tender POS display, and loyalty posting require a real browser/device test. Use the existing $5 test card on a cookie order over $5 to test gift+card. A second order fully covered by a gift card tests the no-remainder path. No real redemption or payment was performed during implementation.
